# Memory — how often, and what for

Memory is not a wrap-up task. Write it when the thing happens, or it does not get
written.

## Cadence

- **Write it in the same turn you learn it.** Do not batch memories for the end of a
  session. A session can end without warning.
- **Check before you assert.** Before you state why something is the way it is, search
  memory. Wrong is worse than slow.
- **Re-read on a scope change.** When the work turns out to be bigger than the request,
  read your memories for that area again.
- **Say what you did.** Report `memory: none written` when nothing qualified. Silence
  reads the same as forgetting.

## What qualifies

Write a memory when the answer would not be obvious to a reader of the code later.

- A decision and the reason for it, especially one you were told twice.
- Feedback on how to work. Include the why.
- A constraint that the code does not show.
- A correction. When you learn a claim was wrong, fix the memory that carried it.

## What does not

- Anything the code, the git history or a tracked issue already records.
- Anything that only matters inside this conversation.
- A restatement of a rule that already lives in this directory.

## Treatment

- One fact per memory. A file that carries three facts gets recalled for the wrong one.
- Link related memories. A link to a memory that does not exist yet is fine.
- Update the index in the same step you add the file.
- Delete a memory that turns out to be wrong. Do not leave it and add a correction
  beside it.
- Convert a relative date to an absolute one.
